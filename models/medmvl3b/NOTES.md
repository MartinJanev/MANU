Model structure (from the code and the checkpoint's config). `LVLMForConditionalGeneration.from_pretrained(<checkpoint>)` builds `LVLMConfig` from `config.json`; `LVLMConfig.from_pretrained` reloads the LLM config (`AutoConfig.from_pretrained("meta-llama/Llama-3.2-3B-Instruct")`) and the M3D-CLIP config by name, with the stored `cache_dir_hf`. The model's `__init__` then loads, by name, Llama-3.2-3B-Instruct (weights and tokenizer, `attn_implementation` from the config) and the whole M3D-CLIP (whose `__init__` loads bert-base-uncased), builds the spatial-pooling connector, and `from_pretrained` loads the checkpoint's state dict over all of it. Every one of these names must be in the offline HF cache, hence the four repos in `env.sh` (the brief listed only the checkpoint). Visual tokens: M3D-CLIP's 8×16×16 = 2048 patch tokens (cls token dropped, last block before the norm), 2×2×2 average pooling to 256, MLP 768 → 3072 → 3072. With the prompt (59-74 ids for the questions of `common/qna.py` in both option orders, counted with the tokenizer below) at most 329 embeddings, under the 512 (`llm_max_length`) at which `prepare_inputs_for_multimodal` truncates. The CT-3B-en recipe (first-commit `scripts/train/MedM-VL-CT-3B-en/*.sh`): pretrain on M3D-Cap with only the connector trained, then fine-tune on M3D data (`m3d_finetune.json`, `M3D/npys_256`) with the LLM and the connector fully trained and M3D-CLIP frozen.

Deviations:
- Repository commit: 4a84399 instead of HEAD. Commit b1b0770 (2025-10-10, "update arguments") renamed every config key to `lvlm_*` (`lvlm_llm_type`, ...); the checkpoint's `config.json` has the old keys (`llm_type`, `llm_config`, `cache_dir_hf`, ...), so HEAD's model `__init__` fails on it (checked: `KeyError: None` at `LLM_FACTORY[config.lvlm_llm_type]`). 4a84399 is the last commit before b1b0770; `configuration_lvlm.py` there is unchanged since the first commit, and building a model with its code gives exactly the checkpoint's top-level config keys (checked). The m3dclip path of `modeling_lvlm.py`, the llama3 loader and the templates are the same at 301eb30 and 4a84399; the M3D-CLIP processor is not (see "Orientation and intensities").
- transformers 4.43.1 instead of the repo's 4.42.4 (see Pins).
- Question format: M3D's "Choices: A. ... D. ..." (style "A"), the checkpoint's trained format, instead of the brief's "(a) ... (d)" (see "Prompt and answer format").
- Decoding: `max_new_tokens=16` (global constraints) instead of the scripts' `max_length 512`; `temperature` not passed (0 in the scripts, which means greedy); `return_dict_in_generate=True, output_scores=True` added, so the text comes from `output.sequences` (only the new tokens, since the LLM gets `inputs_embeds`).
- The item is built in memory: `MultiModalDataset` itself reads a JSON list and `.npy` files from disk.
- `local_checkpoint`: `from_pretrained` gets a temporary folder with symlinks to every file of the snapshot and its own `config.json`, the checkpoint's with `cache_dir_hf` set to null (default cache, `HF_HOME`). With the stored value (the authors' cache folder) the offline job finds nothing (checked: `OSError ... meta-llama/Llama-3.2-3B-Instruct is not the path to a directory containing a file named config.json`).
- Attention: the checkpoint stores `llm_attn_implementation flash_attention_2`. If `transformers.utils.is_flash_attn_2_available()` is false in the job, `local_checkpoint` writes `"sdpa"`, which `LlamaForCausalLM` supports in 4.43.1. No flash-attn install.
- Python 3.12: the conversation templates (`lvlm/dataset/template/*.py`) use formatter instances as dataclass field defaults, which Python >= 3.11 rejects ("mutable default ... use default_factory"; checked on 3.12), so the templates do not import in the image as published (the README asks for Python 3.10). `preload_formatters` imports `formatter.py` under its package name first and gives `EmptyFormatter`/`StringFormatter` the identity hash: the 3.10 behaviour (one shared default instance per template class). The repo's files are not modified. (Same pattern and same shim as models/med2e3.)
- Blank control: the processor min-max scales a constant volume to zeros, where `CropForeground` finds no voxel > 0 and `Resize` rejects the empty crop (checked: RuntimeError). `model_volume` gives such a volume as the zero (1, 32, 256, 256) array the min-max produces, without the crop and resize; every other volume goes through the repo's processor.
- Loading checks (see "Does the loader restore every trained module"): `output_loading_info=True` added to `from_pretrained`; `load()` prints missing/unexpected/mismatched keys and stops if any key is missing; `model.llm.tie_weights()` after loading.
- `MODEL_DTYPE` and `DEVICE` are module constants ("bfloat16", "cuda") so the CPU scratch checks can run in float32 (CPU has no bf16 `avg_pool3d`; the GPU job keeps bf16, as the authors' scripts).

Does the loader restore every trained module? Yes, unlike Med-2E3's per-module loader. MedM-VL loads the whole model with `PreTrainedModel.from_pretrained`, and the checkpoint is `trainer.save_model` of the whole model (`training_recipe/base.py`); the connector's own `load_model(connector_path)` runs only in training's `model.load(...)` and `connector_image3d_path` is null. The shard sizes fit a full bf16 state dict with one copy of the tied embeddings: Llama-3.2-3B (3.21B parameters, 6.43 GB) + M3D-CLIP (vision ViT and BERT, about 0.39 GB) + connector (0.02 GB) = 6.85 GB = 4.97 + 1.88 GB. The index file could not be read, so `load()` prints the loading info (the dev log should show `missing [], unexpected [], mismatched []`) and raises if a key is missing, because `from_pretrained` would give that weight a random initialisation. One trap in transformers 4.43: when the checkpoint's dtype equals the model's, `_load_state_dict_into_model` assigns the loaded tensors instead of copying them (`check_support_param_buffer_assignment`), which unties `llm.lm_head` from `llm.model.embed_tokens`; the checkpoint stores only `embed_tokens` (tied), so `lm_head` would stay at Llama-3.2's own embeddings, and the outer model's `tie_weights()` does not reach the LLM. With the published path the model is built in float32 and the checkpoint is bf16, so the tensors are copied and the tie holds (checked both ways, below); `load()` calls `model.llm.tie_weights()` anyway (a no-op when tied) and prints whether `lm_head` was tied after `from_pretrained`.

Prompt and answer format:
- Used: "<image3d>\n" + M3D's close-ended format "{question} Choices: A. ... B. ... C. ... D. ..." (`format_mcq` style "A", as in models/med2e3), parsed with `parse_choice` style "A". The trained answer is "C. {text}", and after the template's "ASSISTANT:" Llama-3's tokenizer gives " C", ".", ...: the four letters " A", " B", " C", " D" (ids 362, 426, 356, 423) are single tokens at the first answer position, so the letter probabilities are the softmax of the first generated position's scores at those ids, renormalised over the four.
- Why "A" and not the brief's "(a) ... (d)" (controller ruling, fix round 1): the brief's format is that of `examples/data/inference_3d.json`, added on 2025-04-10 (commit 5a90f80) with the CT-Chest model; `examples/inference_3d.sh` runs it on MedM-VL-CT-Chest-3B-en with `--conv_version qwen2` on CT-RATE, and the team notes took it from there. MedM-VL-CT-3B-en is the December 2024 M3D model and was released with M3D's close-ended format: the first commit's (301eb30) `docs/example_finetune.json`, the annotation format of `scripts/train/MedM-VL-CT-3B-en/finetune.sh`, has "<image3d>\nWhere is the saccular aneurysm located within the brain? Choices: A. Insular segment (M2) of left middle cerebral artery B. Basal ganglia C. Frontal lobe D. Temporal lobe" with the answer "A. Insular segment (M2) of left middle cerebral artery" (`docs/example_inference.json` has the same question form); its M3D-Bench close-ended scorer (`scripts/eval/m3d_bench/eval_m3d_vqa_close.py`, run with `--conv_version llama3` on `M3D/npys_256`) counts an answer as correct when `answer_choice + "."` is in the output; and M3D's own `LaMed/src/dataset/multi_dataset.py` builds the training questions as `question + ' ' + "Choices: A. {} B. {} C. {} D. {}"` with the answer "{letter}. {text}". The fine-tune data (`m3d_finetune.json`) itself is not published.

Orientation and intensities:
- Training data (M3D-Cap/VQA `npys_256`, `m3d_cap_data_prepare.py`): Radiopaedia display images (grey, /255) sorted by file number and stacked along axis 0, min-max scaled, `CropForeground`, `Resize([32, 256, 256], "bilinear")`, saved as (1, 32, 256, 256) in [0, 1]. Depth is the series' own plane and order; in-plane as displayed, which for axial series is the radiological display (rows anterior → posterior, columns patient right → left).
- MedM-VL's dataset code (4a84399) does `np.load` and passes the array to the processor without reorientation; the "HU2RGB" lines (clip to [-1000, 1000], scale to [0, 255]) are commented out there and active only from b1b0770 on. The team notes' clip and fixed CT z-score are HEAD's `dataset.py` and `medmclip.py` (mean 55.70, std 66.19 on that 0-255 scale), the MedM-CLIP-CT encoder of the CT-Chest model; this checkpoint uses `m3dclip`.
- The m3dclip processor at 4a84399 (`Image3DProcessor`, from cbff20d, 2025-04-19): `/255`, channel axis, min-max to [0, 1], `CropForeground()`, `Resize([32, 256, 256], "bilinear")`, `ToTensor`: M3D's own preparation steps. At the first commit (when the checkpoint was trained) it was `ToTensor` only, on M3D's already prepared arrays; for those arrays the two agree (min-max, crop and resize are near no-ops), and for ours the later one applies the preparation the training arrays had.
- Ours: `common.volume.load_canonical` (D feet → head, H front → back, W patient right → left) → `to01` → `resize(·, (32, 256, 256))` → `[-1000, 1000]` (pseudo-HU for MRI; for CT-RATE `to01` is the [-1000, 1000] HU window and `to_pseudo_hu` its inverse, so the real HU clipped and resized), no flip. Axis 0 is depth, as M3D-CLIP's 4×16×16 patches expect. The processor's min-max makes the [-1000, 1000] scale irrelevant (checked: the same output as for the [0, 1] volume, max difference 2e-7), and HEAD's HU2RGB would be the identity on it. The in-plane layout matches M3D's axial display images; no source fixes a depth direction. `test_pseudo_hu_range` and `test_ct_rate_gets_clipped_hounsfield_units` pin this.
